# AFC改进思考记录 v4 phase4 词表依赖审计与主链路降权 2026-05-13

## 这份文档和前面几份文档的关系

这份文档是下面两份文档之后的继续执行记录，不是另起炉灶：

- `AFC改进思考记录_v4_phase4_词表抽离与事件词表默认停用_2026-05-13.md`
- `AFC改进思考记录_v4_phase4_题面词表去依赖改造清单_2026-05-13.md`

前两份文档主要解决的是两个问题：

1. 先把“明显押题”的词表从主链路里挪出来，避免它们继续直接驱动 claim 分类和 atomic query 规划。
2. 先做一版清单，知道哪些地方还在偷偷依赖题面词。

这份文档往前再走一步，目标变成：

1. 不只是知道哪里有词表，而是按“影响层级”把它们分层。
2. 先处理最危险的一层，也就是会影响直证据挑选和 supporting/refuting 转换的词表。
3. 让主链路更像“按槽位、文本形状、页面契约来判断”，而不是“按押中的词来判断”。

---

## 本轮我们在解决什么问题

现在的问题不是代码里有词表本身，而是有些词表已经越过了“辅助检索”的边界，开始参与下面这些关键动作：

1. 哪一句证据被当作 answer candidate。
2. 哪一句证据被当作 relation support。
3. 哪个页面标题被判成结构化可用页面。
4. 哪个 claim 被认为像某类 claim。

其中最危险的是前两个。因为一旦“句子候选”阶段就被题面词推着走，后面就算有 slot、ledger、gate，也是在错误候选上做精细推理，最后会出现一种很隐蔽的过拟合：

- 看上去不是直接硬编码标签。
- 但实际上已经在“证据入口”上押中了题。

这类问题如果不先压住，后面继续做 retrieval conversion、decision state、fallback 校准，都会被前面的偏置污染。

---

## 本轮审计的结果

### 一类：可以暂时保留的基础设施词表

这类词表主要做页面治理、反爬识别、route 媒介粗分类、stopword 清洗。它们会影响检索效率，但不会直接决定标签。

当前主要分布：

- `afc_route_markers.py`
- `retrieval.py` 里的 anti-bot / page background / page landing / stopword

当前判断：先保留，但后续要继续做“结构化替代优先，词表兜底”的收缩。

### 二类：中风险词表

这类词表不直接改标签，但会影响页面 readiness、标题 utility、claim family 识别。

当前主要分布：

- `solve.py`
  - `EXCLUSIVE_PREMISE_PATTERN`
  - `EXCLUSIVE_ROUTE_HINT_PATTERN`
  - `INTERPRETIVE_EXPLANATION_PATTERN`
  - `DIRECT_OBSERVABLE_PATTERN`
- `evidence.py`
  - `ANNOUNCEMENT_CLAIM_MARKERS`
  - `NON_ANNOUNCEMENT_EVENT_MARKERS`
  - `MARKET_CALENDAR_CLAIM_MARKERS`
- `retrieval.py`
  - `structured_title_marker_hit`
  - 部分 mode-specific marker 列表

当前判断：这层不是最先要砍的，因为它们多数还处在“页面契约判断”或“claim 形状识别”位置。后续要继续收敛，但本轮不直接大拆。

### 三类：高风险词表

这类词表已经直接参与“证据句选择”或者“support/refute 候选转换”，最容易造成押题。

本轮重点命中两处：

1. `retrieval.py -> answer_candidate_sentence_score`
   - 之前会调用 `ANSWER_MARKER_GROUPS`
   - 本质上是在拿一组题面词给句子加分
   - 这会让“像答案的话术”被优先挑出来

2. `evidence.py -> entity_sentence_has_relation_support`
   - 之前有 `ENTITY_RELATION_SUPPORT_MARKERS`
   - 如果 claim 里恰好带这些词，就会优先看 sentence 是否也带这些词
   - 这相当于用词面重复来替代 relation 级支持判断

3. `evidence.py -> sentence_overlap_score`
   - 之前会因为 `retired / withdraw / beat / won` 这类结果词直接加分
   - 这同样会把“看起来像赛果句”的 sentence 往前推

## 本轮已经落地的改动

### 1. 去掉 `answer_candidate_sentence_score` 对 `ANSWER_MARKER_GROUPS` 的依赖

这一步之后，句子候选排序不再因为：

- `won`
- `beat`
- `announced`
- `price`
- `位于`
- `退赛`

这些词被额外加分。

现在这一路更依赖：

- query core token 命中
- numeric marker 命中
- temporal marker 命中
- route relation 命中
- score pattern 这类文本形状

也就是说，我们保留“结构形状”和“绑定词槽”，去掉“答案腔调词”。

### 2. 去掉 `sentence_overlap_score` 的结果词加分

这一步之后，`sentence_overlap_score` 不再因为“赢了、输了、退赛、walkover”这一类词直接抬分。

现在它更像一个简单的表层重叠分：

- claim token 重叠
- 数字/比分形状

这能减少 event_result 题被固定词表牵着走。

### 3. 去掉 `entity_sentence_has_relation_support` 里的 marker 快捷通道

之前这条链路的问题是：

- 只要 claim 里出现某些 relation 词
- sentence 里也出现同样的词
- 就容易被快速当作 relation support

现在这条链路改成更结构化的判断：

- 先看 claim entity 是否真的在 sentence 中落地
- 再看非实体 relation token 是否形成足够重叠
- 最后才保留一个较弱的 answer_score 兜底

换句话说，之前是“词对词”，现在是“实体落地 + 关系 token 重叠”。

---

## 这一轮做完之后，能力上提升了什么

这一轮不是让更多样本立刻变对，而是先解决一个更根的问题：

### 提升 1：降低“词面押中就像对了”的假阳性

之前有些页面之所以被挑成候选，不是因为它们真的和 claim 同槽对齐，而是因为它们说话方式像答案。

这轮之后，这种假阳性会下降。

### 提升 2：让后面的 slot / ledger / gate 接到更干净的候选证据

我们的主链路已经越来越 evidence-first 了，所以前面的 candidate 质量非常重要。

如果 candidate 本身被词表推歪，后面再精细也没意义。

这轮的价值，就是先把 candidate 池子里的“词表噪声”降下来。

### 提升 3：为下一步的结构化替代创造空间

下一步我们可以更安心地做：

- decision state 统一化
- claim scope 主需/次需显式化
- evidence sentence 的 slot-grounded ranking
- retrieval conversion 的结构化 retry operator

因为前面的候选句层不再那么依赖押题词表。

---

## 这一轮没有解决什么

要很诚实地说，这轮并没有把所有词表都清掉。

目前还没处理完的重点有：

1. `evidence.py` 的 announcement / non-announcement 判别
2. `evidence.py` 的 market calendar state 识别
3. `retrieval.py` 的 structured title marker 判断
4. `solve.py` 里一些 claim shape 的 regex 模式
5. `afc_route_markers.py` 仍然有较多 route 相关词表

但这些还没动，不代表它们都错。只是本轮优先级更低。

因为和“候选句直推标签”相比，这些位置的危害更偏间接。

---

## 当前结论

当前最合理的策略不是“一刀切禁用所有词表”，那样会把系统直接打残；也不是继续容忍词表深入主链路，那样会越来越押题。

更合适的路线是：

1. 先把词表按影响层级分层。
2. 优先清理直接影响证据句选择和 support/refute 转换的词表。
3. 保留一部分页面治理和 stopword 级基础设施词表。
4. 后续再把中风险词表逐步替换成 slot、page contract、decision state、text shape 这些结构信号。

这条路的核心不是“完全不用词”，而是“词不能决定裁决”。

---

## 下一步建议

下一步建议继续做两件事，而且顺序不要反：

### 第一步：继续审计并降权中风险词表

优先看：

- `structured_title_marker_hit`
- announcement/non-announcement
- market calendar state

目标不是直接删，而是改成：

- page role
- evidence contract
- slot completeness
- time binding

这些结构信号优先，词表只做兜底。

### 第二步：把 evidence sentence ranking 改成显式槽位排序

也就是让句子候选排序显式看：

- subject 是否落地
- time_scope 是否落地
- metric_or_relation 是否落地
- status_or_result 是否落地

而不是继续依赖“关键词多不多”。

只有把这一步做出来，我们后面的“候选证据转成同槽直裁证据”才会更稳，也更通用。

## 补充进展：标题 readiness 也开始去词表化

在这份文档初版落地后，我们又继续推进了一小步，把 `retrieval.py -> structured_title_marker_hit` 从“mode 对应词表命中”往“文本形状命中”挪了一层。

### 之前的问题

这个函数原来主要靠下面这类模式来判断标题是不是“像一个可保留的结构化页面”：

- 汇率 / 中间价 / 牌价
- 日期 / 公布 / 发布
- 休市 / 开盘 / 交易日
- 赛果 / 比分 / winner / final

这还不算直接判标签，但它会影响：

1. 页面 soft keep
2. structured penalty recovery
3. 哪些页面有机会继续往后走

所以这里如果太依赖词表，还是会让系统偏向“说话方式像答案”的页面。

### 这一小步怎么改的

现在这块变成更看结构：

- `numeric_fact`
  - 看是否有数字
  - 看是否能抽出数值形状或单位/币种形状
- `date_fact / schedule_fact`
  - 看是否有时间抽取结果
  - 看是否有明确日期形状
- `event_result`
  - 先看结果信号函数
  - 再看是否有比分形状

也就是说，我们把“标题像不像某个题型”的判断，从“先看关键词”逐步改成“先看可抽取结构”。

### 这一步的意义

这一小步不会立刻解决所有过拟合问题，但它把页面保留层也往结构化推进了。

这样一来，现在已经形成了一个比较清楚的方向：

1. 候选句排序不要依赖答案词表。
2. supporting/refuting 入口不要依赖 relation 词表。
3. 页面 readiness 不要过度依赖 mode 词表。

这三块一旦都往结构化推进，后面的 ledger / gate / fallback 才更有机会真正泛化。

## 补充进展：announcement-date 特例开始改成 target 驱动

这轮又往前补了一小步，落在 `evidence.py -> summarize_date_claim` 的 announcement-date 特例上。

### 之前这里的问题

这条分支原来大致是这样工作的：

1. 如果 claim 看起来像“公告/宣布/发布日期”。
2. 同时证据句看起来像“演讲/颁奖/采访/讲座”等非公告事件。
3. 那么即使日期不一致，也先不要把它当成直接反证，而是降成 `date_reference`。

这个思路本身没错，因为它是在防“日期角色串口径”。  
但它的问题也很明显：

- claim 端靠公告词识别自己
- evidence 端靠非公告事件词识别自己

也就是说，这里虽然不是直接改标签，但已经在用词表决定“这个冲突算不算同槽可裁决”。

### 这次怎么改

这次先做了一个保守但更结构化的版本：

1. `claim_is_announcement_date_claim`
   - 优先看 `evidence_target`
   - 当 target 明确是 `publication_date / effective_date / event_date` 时，直接认为这是日期角色题
   - 只有 target 不明确时，才退回到较窄的文本形状兜底

2. `sentence_is_non_announcement_event`
   - 先看页面角色和契约角色
   - 如果页面本身是 `entry / generic / blocked`，直接排除
   - 如果契约角色已经是 `date_authority`，也不把它当成“非公告事件页”
   - 然后再用比分/赛果/退赛这类更接近事件结果形状的信号做兜底

### 这一步的意义

这一步的关键不是“完全去掉文本判断”，而是把顺序改了：

- 之前：先看词，再猜页面是什么
- 现在：先看 target 和 page role，再用文本形状补

这样 announcement-date 这条特例开始更像一条系统规则，而不是一条词表规则。

### 还没做完的地方

这块还没完全去词表化：

- `sentence_is_non_announcement_event` 末端仍然有一层事件结果词形状兜底
- 老的 announcement 词表常量还在文件里，虽然主流程已经不再依赖它们

后面可以继续做两步：

1. 把这两个常量彻底下线
2. 把 `non_announcement_event_page` 的判定继续改成 page utility / contract role / slot role 驱动
