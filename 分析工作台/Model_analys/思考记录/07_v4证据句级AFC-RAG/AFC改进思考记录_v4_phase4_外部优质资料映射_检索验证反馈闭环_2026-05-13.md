# AFC v4 Phase4：外部优质资料映射与检索-验证反馈闭环

日期：2026-05-13

## 0. 这份文档解决什么

这份文档不是简单列论文，而是回答一个工程问题：

> 我们现在遇到的“候选证据不能稳定变成同槽直裁证据”“LLM 看到支持句就忽略反证句”“claim 一次性拆分不够”等问题，到底是不是架构问题？  
> 如果是，外部优质研究和大厂落地给我们的方向是什么？  
> 这些方向能不能落到 AFC 当前架构里？

结论先说：

```text
方向是对的。
下一阶段不应该继续堆兜底，而应该把线性 RAG 改成受控的检索-验证反馈循环。
```

但这个循环不能一上来做大 agent，要先围绕 AFC 已有对象做小闭环：

```text
user_need_slot
-> atomic_claim / field_claim
-> evidence_event
-> same_slot_conflict
-> decision_state
-> decision_policy
-> gap_diagnosis
-> targeted_retrieval
```

## 1. 我们现在的真实问题

### 1.1 LLM 不是不会推理，而是当前结构让它只做单点判断

现在很多验证调用像这样：

```text
claim + 一组 evidence -> supported/refuted/uncertain
```

这会导致一个问题：

```text
LLM 先看到支持句，就容易给 supported；
后面即使有反证句，也不会自动进入“质疑 -> 复核 -> 改判”。
```

`afc_0004` 就是典型：

```text
claim：覃予萱 3-0 获胜
候选支持：页面里有 3-0
候选反证：考夫蔓退赛 / 比赛取消 / 不战而胜
```

如果没有反证优先和同槽冲突复核，LLM 很容易只吃关键词。

这不是单纯 prompt 问题，而是：

```text
证据极性识别
同槽冲突检测
反证优先复核
最终裁决
```

这几层没有分开。

### 1.2 原子 claim 不能一次性拆完

我们现在的原子 claim 主要是前置抽取：

```text
answer -> claim / atomic_claim
```

但很多 claim 只有检索后才知道应该怎么拆。

比如：

```text
印度人口普查结果什么时候出
```

检索后才会暴露多个候选槽：

```text
第一阶段开始
第二阶段开始
普查结束
结果公布
数据发布
```

这说明原子分解需要反馈：

```text
初始 claim
-> 检索
-> 发现证据槽位混乱
-> 重新分解成字段级 claim
-> 再检索
-> 再验证
```

### 1.3 主需/次需不能继续主要靠 LLM 初判

现在 `centrality=core/supporting/peripheral` 主要来自抽取阶段 LLM，再由 `answer_role_impact` 和后处理少量修正。

这还不够。

更稳的方式应该是：

```text
question -> user_need_slot
claim -> answer_role
claim 是否直接填 user_need_slot -> 决定 core/supporting
```

主需不是“显眼事实”，而是：

```text
能直接回答用户问题的事实槽。
```

高风险细节如果不直接填用户问题槽，原则上是次需；但如果它是主结论成立的必要前提，应单独标成：

```text
core_premise
```

### 1.4 搜索结果不稳定会破坏回归

同一个 query 不同时间返回不同结果，导致：

```text
这次判对
下次判错
不知道是代码变了还是搜索变了
```

所以 AFC 后面必须把在线检索和可复现实验分开：

```text
query_plan freeze
search_result cache
page_snapshot cache
evidence_event replay
```

否则评估会一直发虚。

## 2. 外部研究给我们的核心启发

### 2.1 Claim verification 数据集常常只测到词面匹配

资料：

- What Do Claim Verification Datasets Actually Test? A Reasoning Trace Analysis  
  https://arxiv.org/abs/2604.01657

它的重点是：

```text
很多 claim verification benchmark 表面在测事实验证，
实际大量样本主要考 direct evidence extraction / lexical matching。
复杂多句综合、数值推理反而不足。
```

对我们的启发：

```text
不能因为 LLM 在普通验证 benchmark 上表现好，就相信它能自动处理 AFC 里的阶段边界、数值口径、反证优先和跨 claim 一致性。
```

这支持我们把：

```text
词面相关 evidence
```

和：

```text
同槽可裁决 evidence
```

明确分开。

### 2.2 Decomposition 的瓶颈不是拆，而是 evidence alignment

资料：

- The Alignment Bottleneck in Decomposition-Based Claim Verification  
  https://arxiv.org/abs/2602.10380

它的重点是：

```text
claim decomposition 只有在 evidence 也精确对齐到 sub-claim 时才有效。
如果只是把同一批 claim-level evidence 重复喂给所有子 claim，效果可能不升反降。
```

对我们的启发：

```text
不能只做 atomic_claim。
必须让每个 atomic_claim 有自己的 slot_contract、query、evidence_event 和 same_slot 判断。
```

这正好解释我们现在的 `candidate_unconverted`：

```text
claim 拆了，但 evidence 还没有对齐到字段。
```

### 2.3 迭代式 claim 编辑比一次性拆分更适合对抗样本

资料：

- SUCEA: Reasoning-Intensive Retrieval for Adversarial Fact-checking through Claim Decomposition and Editing  
  https://arxiv.org/abs/2506.04583

它的重点是：

```text
先把复杂 claim 拆成独立 sub-claim，
再迭代检索 evidence，
再根据检索结果编辑 subclaim，
最后聚合证据和标签。
```

对我们的启发：

```text
maybe_decompose_compound_claims 不能只是一次性正则拆分。
它应该被升级为“检索后重拆/重写”的受控 operator。
```

但我们不能直接照搬成大 agent，而应该先做小闭环：

```text
candidate_unconverted
-> gap_diagnosis
-> field_claim_rewrite
-> targeted_retrieval
```

### 2.4 FIRE 支持“检索-验证循环”，不是线性 RAG

资料：

- FIRE: Fact-checking with Iterative Retrieval and Verification  
  https://aclanthology.org/2025.findings-naacl.158/

它的重点是：

```text
fact-checking 需要 iterative retrieval and verification。
验证不确定时，不应该直接输出最终 verdict，而应该继续找更有用的证据。
```

对我们的启发：

```text
AFC 现在不能停在一次 retrieve。
当 decision_state 显示 candidate_unconverted / partial_incomparable / date_only_guarded 时，
应该触发下一轮 targeted retrieval，而不是直接 fallback。
```

### 2.5 ThinknCheck 支持“短 rationale + verdict”的可解释裁决

资料：

- ThinknCheck: Grounded Claim Verification with Compact, Reasoning-Driven, and Interpretable Models  
  https://arxiv.org/abs/2604.01652

对我们的启发：

```text
reason_builder 方向是对的。
最终 reason 不应该只是 verdict 后的装饰，而应该是结构化裁决路径的压缩说明。
```

当前 CR6 已经做了第一步：

```text
decision_state -> reason_builder
```

下一步应该让 reason 继续读取：

```text
gap_diagnosis
same_slot_conflict
cross_claim_graph
```

### 2.6 ClaimDB 支持字段级/结构化验证

资料：

- ClaimDB: A Fact Verification Benchmark over Large Structured Data  
  https://arxiv.org/abs/2601.14698

对我们的启发：

```text
自然语言 query 不够。
很多 AFC 问题需要字段级查询计划。
```

例如：

```text
subject = 覃予萱
object = 考夫蔓
event_role = actual_result
exception = withdrawal_or_walkover
time_scope = 2026-03-31
```

这不是要真写 SQL，而是要让检索计划具备 SQL-like 字段约束。

### 2.7 DiVA 支持细粒度 factuality verification

资料：

- DiVA: Fine-grained Factuality Verification with Agentic-Discriminative Verifier  
  https://arxiv.org/abs/2601.03605

对我们的启发：

```text
AFC 不应该只做最终 0/1/2。
中间要保留细粒度状态：
direct_supported
direct_refuted
candidate_unconverted
partial_incomparable
date_only_guarded
cross_claim_conflict
```

这和我们现在的 `decision_state` 是一致的。

### 2.8 Evidence retrieval 要从 relevance 转向 utility

资料：

- From Relevance to Utility: Evidence Retrieval with Feedback for Fact Verification  
  https://arxiv.org/abs/2310.11675

对我们的启发：

```text
检索排序不能只看相关性。
要看这条证据能不能被 verifier 真正用来裁决。
```

换到 AFC，就是：

```text
可裁决性 > 相关性
同槽反证 > 普通支持
结构化事实句 > 泛背景页
```

## 3. 大企业落地给我们的工程启发

### 3.1 OpenAI Knowledge Retrieval：trusted answers 依赖 citations + evals

资料：

- OpenAI Knowledge Retrieval  
  https://openai.com/solutions/blueprints/knowledge-retrieval/

它强调：

```text
grounded answers
citations
evals
reference architecture
```

对我们的启发：

```text
AFC 不能只输出 label。
必须把 evidence_ledger、source、reason、policy_route 一起作为产物。
```

这和我们 CR6/CR7 的方向一致。

```text
遵守企业权限。
```

对我们的启发：

```text
AFC 里的“冲突证据”不应该是噪声，而应该成为触发二次检索和二次裁决的信号。
```

### 3.3 Microsoft Copilot Retrieval API：企业检索必须有权限、结构化查询和上下文召回

资料：

- Microsoft 365 Copilot Retrieval API  
  https://learn.microsoft.com/en-us/microsoft-365/copilot/extensibility/api/ai-services/retrieval/overview

```text
它会有授权边界、上下文、结构化检索语言或过滤条件。
```

对应 AFC：

```text
query 应该升级成 field-level query plan。
```

### 3.4 Microsoft GraphRAG：关系结构进入检索主链

资料：

- Microsoft GraphRAG  
  https://www.microsoft.com/en-us/research/project/graphrag/

```text
很多 AFC 错误不是单句文本相似度问题，而是关系问题。
```

例如：

```text
阶段开始 vs 阶段结束
前提 vs 结论
历史状态 vs 当前状态
主体 A vs 主体 B
```

这些更适合用 graph/state 表达，而不是只靠 top-k 文本。

### 3.5 Google Vertex AI Grounding：新鲜性、引用和 enterprise grounding

  https://docs.cloud.google.com/vertex-ai/generative-ai/docs/grounding/grounding-with-google-search

```text
企业控制
```

```text
我们需要把搜索结果快照、引用来源、页面角色、证据句角色固化下来。
```

### 3.6 AWS Bedrock Knowledge Bases GraphRAG：graph + retrieval 已经产品化

对我们的启发：

```text
关系驱动检索不是研究玩具，已经进入大厂产品化。
```

对应 AFC：

```text
phase_graph、cross_claim_graph、same_slot_graph 是合理方向。
```

### 3.7 AWS Q Business Agentic RAG：动态规划检索，而不是固定 top-k

资料：

- Amazon Q Business launches Agentic RAG  
  https://aws.amazon.com/about-aws/whats-new/2025/08/qbusiness-launches-agentic-rag/

对我们的启发：

```text
固定 query -> 固定 top-k -> 一次回答
```

不够。

AFC 应该走：

```text
初始检索
-> 评估证据是否可裁决
-> 缺什么字段就补什么查询
-> 再检索
```

## 4. 哪些我们应该吸收，哪些先不要吸收

### 4.1 应该吸收

#### A. 受控反馈循环

```text
decision_state 不闭合
-> gap_diagnosis
-> field_query_rewrite
-> targeted_retrieval
-> evidence_event re-ingest
```

#### B. 字段级 query plan

从：

```text
自然语言 query
```

升级到：

```text
subject / object / metric / time_scope / evidence_role / refutation_target
```

#### C. 反证优先排序

从：

```text
relevance first
```

升级为：

```text
refutation utility first
```

#### D. 跨 claim 一致性图

把以下内容做成独立裁决维度：

```text
算术一致性
阶段顺序
预测 vs 已发生
当前 vs 历史
前提 vs 结论
```

#### E. 可回放证据快照

把在线检索变成可复现实验：

```text
query_plan
search_results
page_snapshot
evidence_event
decision_state
```

### 4.2 先不要吸收

#### A. 不要直接上多 agent 辩论

多 agent 看起来强，但现在会带来：

```text
成本高
不可复现
debug 更难
标签来源更不清楚
```

我们应该先做：

```text
单链路小闭环 + 结构化状态
```

#### B. 不要让 LLM 直接接管最终标签

LLM 可以做：

```text
gap diagnosis
query rewrite
claim editing
reason polish
```

但最终标签仍应由：

```text
evidence_state + decision_policy
```

控制。

#### C. 不要按样本补转换器

转换器必须按事实槽写：

```text
market_calendar_status
event_result_status
phase_boundary_time
numeric_quote_or_metric
current_position_distance
exclusive_or_only_path
```

不能按：

```text
afc_0004
afc_0007
```

写。

## 5. 对 AFC 当前架构的映射

### 5.1 当前架构能实现什么

当前已经具备：

```text
claim / atomic_claim
retrieval
evidence_event
phase_graph
decision_state
decision_policy
reason_builder
```

它能解决：

```text
证据状态可观测
兜底权限可控
date-only 假反证可拦截
部分原子反证可直裁
reason 可读性提升
```

### 5.2 当前架构解决不了什么

还不能稳定解决：

```text
检索后重拆 claim
字段级 query 动态生成
support/refute 冲突后的反证优先复核
跨 claim 一致性裁决
搜索结果可复现
```

### 5.3 应该补的下一层

建议新增：

```text
gap_diagnosis.py
field_query_planner.py
evidence_replay_cache.py
cross_claim_graph.py
```

但顺序不能乱。

## 6. 推荐下一阶段落地顺序

### CR9：Centrality Calibrator

目标：

```text
让主需/次需从 user_need_slot 出发，而不是主要靠 LLM 初判 centrality。
```

实现：

```text
question -> user_need_slot
claim -> answer_role
claim 是否填 user_need_slot -> 校准 centrality
```

解决：

```text
0/1 标签不稳
高风险细节误上提主需
直接回答用户问题的 claim 被降成 supporting
```

### CR10：Gap Diagnosis

目标：

```text
把 candidate_unconverted 拆成具体缺口。
```

例如：

```text
missing_subject_binding
missing_time_role
missing_metric_type
support_refute_conflict_unresolved
phase_role_ambiguous
```

解决：

```text
现在只知道未闭合，不知道该补什么。
```

### CR11：Field-level Query Planner

目标：

```text
根据 gap 生成字段级 query。
```

例如：

```text
subject=覃予萱
object=考夫蔓
event_role=actual_result
include_exception=withdrawal
```

解决：

```text
自然语言 query 太泛，反证被淹没。
```

### CR12：Refutation-first Evidence Ranking

目标：

```text
supporting/refuting 分队列；
同槽反证优先进入 verifier。
```

解决：

```text
支持证据先被读到，反证证据被忽略。
```

### CR13：Cross-claim Consistency Graph

目标：

```text
内部逻辑矛盾独立成裁决维度。
```

解决：

```text
2-2 这种内部算术矛盾不应该依赖外部检索。
```

### CR14：Replay Cache

目标：

```text
固定 search result / page snapshot / evidence_event。
```

解决：

```text
搜索波动导致回归不可复现。
```

## 7. 当前结论

外部资料和大厂落地共同指向一件事：

```text
成熟的事实验证/企业 grounding，不是一次性 RAG。
```

它们都在往：

```text
多轮检索
字段约束
证据对齐
关系图
引用和评估
可控权限
可解释输出
```

方向走。

对 AFC 来说，最合适的路线不是“大 agent 化”，而是：

```text
在现有 evidence_event / decision_state / decision_policy 基础上，
补一个小而硬的检索-验证反馈闭环。
```

下一刀最值得做的是：

```text
CR9 Centrality Calibrator
```

因为主需/次需是最终 0/1 的根。

如果主需槽没稳，后面的证据链即使找对了，也可能把 0/1 打错。
