## 2026-05-11 伪证据污染差分审计与诚实性修复

### 分类

证据链 / Workflow / 测试与回归

### 这次要做什么？

这轮承接 `BSBTBU首轮实施状态同步` 后的下一步审计，不再直接问“这轮是不是已经把证据抓准了”，而是先回答一个更根的问题：

1. 当前看到的 `kept -> candidate -> point` 进展，到底有多少是真网页证据在推进
2. 有多少只是 `computed / input_context` 这类内部辅助项在冒领进展
3. 如果先把这层泡沫挤掉，系统还剩下多少真实可消费证据

同时按固定思路推进并汇报：

1. 基于什么架构
2. 实现了什么
3. 解决了什么
4. 还卡在哪
5. 现有方案还能不能继续解
6. 如果不能，再去外部检索

### 动机是什么？

前一轮最容易让人误判的地方是：我们看到了不少 `candidate_progress_from_kept_page`，很容易顺着这个现象得出“证据已经能被消费了”的乐观结论。

但成功 run 和失败 rerun 一做差分，问题就暴露出来了：

1. 同一批样本 rerun 时进展不稳定
2. 很多 top candidate 实际不是网页证据，而是：
   - `样本日期星期计算`
   - `汇率数值换算线索`
   - `用户问题主需`
3. 还有一部分“直证”其实是错位页面，例如年份页、日历页、泛百科页

所以这轮真正的动机不是再追一个表面成功率，而是先把“伪成功”从“真成功”里剥出来。只有这样，后面无论是继续补入口、补 kept page，还是补 point conversion，方向才不会跑偏。

### 对我们的项目有什么实际作用？

这轮最大的实际价值，不是把标签立刻抬高，而是把“系统到底有没有真的拿到可裁决证据”这件事说实话。

具体作用有三层：

1. 让 `candidate_progress_from_kept_page` 不再被内部辅助项冒领
2. 让 `stable_direct_point` 不再因为“有一个 direct_answer=direct 的错位点”就提前成立
3. 把后续主瓶颈重新收口到真正还没解决的层：
   - kept page 质量
   - authority/source_type 误归类
   - claim 分解漂移
   - query/official discovery 漂移

这会直接影响我们下一步到底该继续打 retrieval，还是该回头打 page contract 和 point comparability。

### 具体场景又是什么？

这轮主要围绕 anchor 5 题和 rerun 差分看：

1. `afc_0001`
   - 之前出现过“看起来已有 kept page progress”
   - 但 top candidate 常被 `样本日期星期计算` 占住

2. `afc_0008`
   - 之前甚至会被打成 `stable_direct_point`
   - 但实际上更多是汇率相关页，不一定是同一事实位点

3. `afc_0010`
   - 更典型，年份页/日历页/百科页会误入 direct 轨道
   - 这是最危险的假阳性来源之一

4. `afc_0002`
   - 作为保底锚点，必须继续稳定为 `1`
   - 说明我们在清理伪证据时不能把真实 closure 线一起误伤

### 我们基于什么架构？

这轮没有换架构，仍然基于现有主框架继续推进：

1. 受控 Search Tool
2. authority-first 入口
3. Playwright 受控救援
4. 双通道裁决
5. kept page -> candidate -> point 三层消费
6. comparability / point contract / same-slot review

也就是说，这轮不是重新发明新框架，而是在现有框架里修“证据消费诚实性”。

### 这轮实际实现了什么？

#### 1. `solve.py` 新增伪证据识别

新增 `is_pseudo_evidence_candidate(...)`，明确把以下候选识别为伪证据：

1. `source_type in {"computed", "input_context"}`
2. `source in {"computed", "input_context"}`
3. 标题命中：
   - `样本日期星期计算`
   - `汇率数值换算线索`
   - `用户问题主需`

#### 2. decision-useful rerank 不再把伪证据当成有效进展

对伪证据做了两层收口：

1. `candidate_decision_useful_score(...)` 直接大幅降分
2. `decision_useful_hit_for_candidate(...)` 对伪证据直接返回 `False`

同时显式记录：

1. `is_pseudo_evidence`
2. `top_candidate_is_pseudo`
3. `top_evidence_candidate_title`
4. `top_evidence_candidate_profile`

#### 3. kept-page progress 只有真实网页候选才能触发

`infer_slot_review_outcome(...)` 现在只有在存在真实 `top_evidence_candidate` 且 top candidate 不是伪证据时，才允许进入：

1. `same_slot_review_not_direct`
2. `kept_page_candidate_progress`

也就是说，内部辅助项可以继续留在候选池里做诊断，但不能再冒领“网页证据已经被消费”的状态。

#### 4. `stable_direct_point` 从“有 direct 就算”收紧成“有可比 direct 才算”

这轮第二刀更关键：

过去 `stable_direct_point` 只要发现 `claim_direct_supporting_points` 或 `claim_direct_refuting_points` 非空就会成立。

现在改成只有 `comparability_profile` 里存在：

1. `comparable_direct_support_count > 0`
2. 或 `comparable_direct_refute_count > 0`

才允许进入 `stable_direct_point`。

这一步直接打掉了 `afc_0010/c1` 这种“年份页/日历页/百科页被误判成稳定直证”的假成功。

### 解决了什么？

这轮解决的不是“证据成功率已经打通”，而是更基础但必须先解决的问题：

#### 1. 伪证据不再冒领 kept-page consumption

最直接的变化：

1. `afc_0010/c1`
   - 修前会落到 `stable_direct_point`
   - 修后变成 `weak_candidate_retained`

2. `afc_0008/c1`
   - 修前会被当成 `stable_direct_point`
   - 修后变成 `same_slot_reviewed_but_blocked`

这两个变化都说明：系统现在对“是否已经形成稳定直证”更诚实了。

#### 2. 主锚点没有被误伤

`afc_0002` 继续稳定为 `1`，而且 `c1` 仍然是：

1. `top_candidate_is_pseudo = false`
2. `slot_review_outcome = stable_direct_point`

说明这轮修的是假进展，不是把真实证据链整体打塌。

#### 3. 输出 reason 更接近真实阻塞层

二次复验后，主 reason 更稳定地落在：

1. 页保留没稳住
2. 有相关材料但不是同一事实位点
3. 不是纯 recall 黑盒

这比“表面上看起来有 candidate progress”但其实来自内部辅助项，要诚实得多。

### 还卡在哪？

这轮之后，主问题比之前更清楚了，而且不是一个点，而是三层叠加：

#### 1. kept page 本身质量还是不稳

即使把伪证据拿掉，仍然能看到一些可疑 top evidence title，例如：

1. `Is it time to upgrade from Microsoft Office?...`
2. `Antarctica - National Geographic Society`
3. `消息`
4. `forex`

这说明当前还有：

1. 页级保留误收
2. authority/source_type 误归类
3. page utility profile 还不够硬

#### 2. 成功率仍然没有稳定打通

这轮重跑后虽然诚实性更高了，但“关键证据成功率明显变高”这条还不能说通过。

目前更像是：

1. 我们证明了之前有一部分成功是伪成功
2. 真正的稳定成功率还没有被打通

#### 3. 时延仍然高于 BSBTBU 首轮基线

当前 3 次关键回看：

1. `phase4_bsbtbu_sample0410`
   - `avg_seconds = 75.791`
   - `retrieve = 16.855`

2. `phase4_bvbwby`
   - `avg_seconds = 116.115`
   - `retrieve = 33.677`

3. `phase4_bvbwby2`
   - `avg_seconds = 93.964`
   - `retrieve = 24.392`

第二次修正后时延比第一次诚实性修复 run 收回了一些，但仍高于 BSBTBU 首轮基线，所以“成功率更高且用时更短”这个停点依然没到。

#### 4. claim 分解和 source 漂移仍然存在

之前差分审计已经看到：

1. claim id/claim text 会漂
2. official discovery 命中会漂
3. kept page 集合会漂

这部分这轮没有解决，只是让下游消费层变得更诚实。

### 现有方案还能不能继续解？

还能，而且下一步仍然值得优先在现有架构内继续解。

原因很明确：

1. 这轮已经证明当前问题里有一大块是“消费层把假进展当真进展”
2. 修完之后，主瓶颈明显下沉到了 kept page 质量和 authority/source_type 质量
3. 这两层都还在现有方案可解释范围内：
   - page contract
   - authority entry
   - source health
   - page utility / kept-page review
   - comparability gate

所以现在还不到“必须推翻现有架构”的程度。

### 如果不能，再去外部检索？

当前还没到必须再开一轮外部检索的时候。

只有下面这些情况同时出现，才值得再去外部对标：

1. 把 kept page 误收和 authority/source_type 误归类继续收紧后
2. 关键样本仍然长期只能拿到：
   - 泛页
   - 标题页
   - 错位页
   - 非同位点页
3. 且 Playwright / authority-first / page contract 都解释不了

那时再去看 2026 最新的：

1. browser-grounding
2. hosted search / grounding API
3. retrieval contract / page trust calibration

才是合理时机。

### 对用户意味着什么？

对使用者来说，这轮最重要的不是标签有没有突然变好，而是：

1. 系统少了一批“看起来已经拿到证据、其实没有”的假象
2. 当系统说“现在还不能判错”时，这句话比之前更可信
3. 后面如果我们再宣布“这题证据真的打通了”，含金量会更高

### 对开发者意味着什么？

对开发者来说，这轮把下一步真正该打的层明确压缩出来了：

1. 不要再把时间花在“伪 candidate progress”上
2. 下一步优先打：
   - kept page 误收
   - authority/source_type 误归类
   - page utility / page contract 真收口
3. 然后再看 route / point conversion / query family 是否需要继续深打

### 当前结论

这轮不能说“证据已经抓准了”，但可以明确说两件事：

1. 我们已经把一大块伪进展清出来了
2. 现在系统暴露出来的剩余问题，终于更接近真实 retrieval / kept-page / comparability 瓶颈了

换句话说，这轮不是成功率突破轮，而是成功率突破前必须完成的“诚实性修复轮”。

### 下一步建议

下一步不建议再泛泛说“继续打成功率”，而是固定落到一轮更聚焦的 kept-page 质量修复：

1. 基于什么架构
   - 继续沿用现有 `authority-first + kept-page contract + comparability` 架构

2. 实现什么
   - 增加 kept page 真实性 gate
   - 收紧 authority/source_type 误归类
   - 对明显泛页/标题页/错位页增加 hard negative

3. 解决什么
   - 让真正留下来的页更像“可裁决证据页”，而不是“相关但错位的页”

4. 如果还没解决
   - 再看是不是官方入口规划、query plan 或 source family 还在漂

5. 如果现有方案不能继续解
   - 再去看外部最新的 grounding / browser-agent / hosted search 方案
