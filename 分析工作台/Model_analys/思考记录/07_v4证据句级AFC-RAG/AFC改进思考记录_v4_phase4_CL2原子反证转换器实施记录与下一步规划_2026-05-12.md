## 1. 本文和前序文档的关系

CI 文档证明的是“原子 claim 路线值得走”：系统能从长回答里抽出更小、更硬、更接近人工标准 reason 的风险事实点，例如：

- `market_calendar_status`：A股是否休市、是否节假日。
- `event_result_status`：比分、退赛、不战而胜。
- `exclusive_or_only_path`：唯一通道、只能经过、替代路径。
- `phase_boundary_time`：阶段开始、结束、结果公布。

CK/CL 第一轮证明的是“原子 claim 可以进入检索和账本”：不再只是抽出来展示，而是能进入 `atomic_query_plan / atomic_claim_route_debug / atomic_unresolved_points`。

本文记录的是 CL2：把其中一部分原子 claim 从“定位到风险点”推进到“能形成可裁决反证点”。核心不是扩大检索，而是补 `atomic claim -> evidence candidate -> atomic_refuted_point` 的安全转换器。

## 2. 分类

证据链路 / 原子 claim 路由 / 聚合裁决 / 测试回归

## 3. 这次做了什么

本轮主要改动文件：

- `solve.py`
- `retrieval.py`
- `AFC改进思考记录_v4_phase4_下一步计划_CI高风险原子claim路由_2026-05-12.md`

核心改动：

1. 增加 `market_calendar_status` 的原子反证转换。
   - 把“今天/今日/当日”绑定到样本输入时间。
   - 对 `2026-04-01` 这类绝对日期生成可计算日历判断。
   - 对“清明假期休市”这类明确节假日断言，允许形成窄口径计算型反证：`不在清明假期窗口`。

2. 收紧 `event_result_status` 的转换。
   - 赛事结果类不能把日期片段当比分。
   - 高比分赛事如篮球的 `117-86`，不能被 `1-3` 这类小比分、赛季交锋或战绩片段反驳。
   - 只有“比分量纲兼容”或“退赛/弃权/不战而胜”状态明确出现时，才允许进入原子反证。

3. 改造 atomic market-calendar query。
   - 不再沿着错误断言“休市”硬搜。
   - 改成对照式查询：`主体 + 绝对日期 + 交易日历/是否开市/正常交易/官方公告`。

4. 保持安全边界。
   - `risk_type` 本身仍不能直接改标签。
   - `entry_page / generic_page / blocked_page / pseudo_evidence` 仍不能直接驱动标签。
   - 只有 `market_calendar_status` 的计算型日期窗口证据开了窄口；它只证明“日期是否在某个命名节假日窗口”，不证明任意交易状态。

## 4. 动机是什么

人工标准 reason 关心的不是“大段回答整体像不像”，而是小事实点是否错：

- `afc_0001`：4月1日不是清明节假期，A股不应被说成因清明休市。
- `afc_0002`：回答自己说此前双方各胜一场，加上本场黄蜂赢，应为 2-1，不是 2-2。
- `afc_0004`：退赛/不战而胜不能写成具体 3-0 小分。
- `afc_0007`：人口普查第二阶段开始不等于整个人口普查结束。

CI 已经能把这些“刀口”抽出来，但如果转换器太松，就会把伪冲突当反证；如果转换器太紧，就永远停在 `retrieved_waiting_gate`。CL2 的动机就是在这两者之间找到一条可控路径：只让高置信、同槽、可解释的原子冲突进入裁决。

## 5. 对项目的实际作用

本轮的实际价值有三点：

1. 证明原子 claim 不只是诊断字段，可以真正进入裁决链。
2. 将 `afc_0001` 从“知道可疑但不能判”推进到“可形成原子反证并输出标签 1”。
3. 避免 `afc_0008 / afc_0010` 这类无错汇率样本被中等强度数值差异误抬。

这说明提升方向不是盲目扩大 provider、fallback 或 query 数，而是要补“证据消费转换器”。

## 7. 当前结论

CL2 有效，但只打通了第一类原子反证：日历/节假日窗口类。

当前可以确认：

- 原子 claim 路线是对的。
- 对照式 query 比复述错误断言更合适。
- 转换器必须按风险类型分开写，不能一个“numeric conflict”吃所有场景。
- Playwright 和 LLM 应该作为受控升级工具，而不是无条件放大检索。

当前还没解决：

- `exclusive_or_only_path`：替代管道/港口/绕开海峡材料如何安全转成“唯一通道”反证。
- `event_result_status`：退赛/不战而胜页面如何优先于泛体育比分页。
- `phase_boundary_time`：第一阶段/第二阶段/结束/公布之间如何做边界转换。
- `afc_0005`：错误标签有了，但 reason 源串污染，说明证据消费层还要再加 source/page 对齐。

## 8. 下一步规划：CM/CL3 受控 Playwright + LLM 页面消费升级

### 8.1 下一步目标

下一步不是扩大所有样本检索，而是只对“已经接近成功但卡在页面消费”的原子 claim 做升级。

目标：

- 让 `retrieved_waiting_gate / raw_only_filtered_or_gate_pending` 的 atomic 点，能通过 Playwright 抓正文、LLM 判页面角色和同槽关系。
- 让 LLM 只输出结构化 gate 判断，不直接输出最终标签。
- 继续保护 `afc_0008 / afc_0010` 不被中等冲突误抬。

### 8.2 触发条件

只在以下条件触发 Playwright/LLM：

- `atomic_gate_blocked_points` 非空。
- `atomic_unresolved_points.state` 为 `retrieved_waiting_gate`。
- `atomic_stop_reason` 属于：
  - `authority_pair_attempted_no_progress`
  - `raw_without_kept_atomic_evidence`
  - `sogou_html:sogou_slow_after_rescue_available`
  - `page_gate_not_ready`
- `risk_type` 属于：
  - `exclusive_or_only_path`
  - `event_result_status`
  - `phase_boundary_time`
  - `current_position_distance`

不触发：

- `numeric_quote_or_metric` 的普通中等冲突。
- `candidate_conflict_profile.conflict_strength != strong` 的汇率/行情口径差异。
- 已经被判为 `pseudo_evidence` 且没有官方/新闻/结构化页面迹象的材料。

### 8.3 Playwright 负责什么

Playwright 只负责补正文和页面结构：

- 抓取网页正文、标题、发布时间、表格、赛程/结果块。
- 尽量补全 `page_role` 所需字段。
- 对慢源、动态页、搜索摘要不足的页做一次正文 rescue。

Playwright 不负责：

- 不直接决定 label。
- 不绕过 source/page gate。
- 不把搜索结果页当证据页。

### 8.4 LLM 负责什么

LLM 只做结构化页面消费判断，输出 JSON：

- `is_evidence_page`
- `same_subject`
- `same_time_scope`
- `same_metric_or_relation`
- `same_status_or_result`
- `conflict_type`
- `conflict_strength`
- `claim_value`
- `evidence_value`
- `short_reason`
- `should_convert_to_atomic_refuted_point`

LLM 不负责：

- 不直接给最终标签。
- 不输出自由 reason 覆盖证据账本。
- 不允许在没有 URL、原句、槽位的情况下制造反证。

### 8.5 优先样本

优先级一：

- `afc_0004`：退赛/不战而胜 vs 虚构 3-0 比分。
- `afc_0007`：人口普查阶段边界，第二阶段开始 vs 普查结束。

优先级二：

- `afc_0003`：唯一海上通道 vs 替代管道/港口。
- `afc_0005`：距离/位置 reason 污染收口。

守门样本：

- `afc_0008`
- `afc_0010`

### 8.6 验收标准

最低验收：

- `afc_0001` 继续为 `1`。
- `afc_0002` 继续为 `1`。
- `afc_0008 / afc_0010` 继续为 `2`。
- 至少一个 `retrieved_waiting_gate` 样本推进到更明确的页面消费诊断。

进阶验收：

- `afc_0004` 或 `afc_0007` 至少一个形成 `atomic_refuted_points`。
- 若形成强反证，ledger 必须能追到：
  - 原子 claim
  - URL
  - 证据原句
  - 冲突槽位
  - page/slot gate 通过原因

性能要求：

- retrieve 均值不超过当前 CL2 8 样本基线 `57.245s` 的 10%。
- 如果超过，只保留 Playwright/LLM 的诊断输出，不让其参与标签聚合。

## 10. CM/CL3 首轮实施记录：事件表格行到原子反证

日期：2026-05-12

### 分类

证据链路 / 原子 claim 路由 / 检索转换器 / 聚合裁决

### 这次要做什么

本轮沿着上面的 CM/CL3 计划，先不引入新 provider，也不扩大 fallback，而是把 `event_result_status` 里最容易泛化的一类场景打通：答案中出现 Markdown 表格，表格行含有“主体、项目、对阵、比分、状态”时，把每一行转成独立的高风险原子 claim。

这次改动只覆盖通用结构：

- 表格行抽取：`主体 | 项目 | 对阵 | 比分/赛果 | 状态`
- 事件对手抽取：`A vs B score`、`A 对阵 B score`、`A score B`
- 详细比分识别：`3-0 (11-9, 11-8, 11-6)` 这类带小局/分节细节的值
- 退赛/弃权/不战而胜识别：`退赛`、`弃权`、`不战而胜`、`walkover`、`withdrawal`

### 动机是什么

标准 reason 关心的不是“有没有搜到赛事新闻”，而是“回答写了具体小比分，但真实事件是退赛/不战而胜”。如果只把整段答案当作一个 claim，检索会变成“国乒 4 场 3-0”，很容易搜到泛体育页或同赛事概览，却打不到具体错点。

因此需要把表格行拆成最小可反证单元：某主体、某对手、某日期、某具体比分状态。这样换一道题，只要也是结构化赛果表、比赛结果表、选手对阵表，仍然可以复用同一套转换器。

### 对项目的实际作用

1. `event_result_status` 不再只停留在“发现有赛果风险”，而能把表格中的单场事件变成可检索、可消费、可进账本的原子点。
2. 检索 query 不再携带完整小局分，避免过窄；查询只保留主体、对手、主比分和退赛/弃权对照词。
3. 反证转换更安全：只有“详细比分 claim + 同一参赛双方 + 退赛/弃权/不战而胜证据”同时满足，才升为强原子反证。
4. 聚合层开始消费 `atomic_refutation_decision_signal`，并保护 `atomic_core_direct_refutation` 不再被后置 review 降回证据不足。

### 具体场景是什么

适用场景：

- 乒乓球、网球、羽毛球、电竞等可能出现退赛/弃权/不战而胜的单场结果。
- 回答用表格给出多场比赛的具体比分。
- 证据页说的是 walkover/withdrawal/retired/退赛，而回答却编出了每局比分。

不适用场景：

- 只有总比分 `3-0`，证据也说“按规则 3-0 获胜”，这不直接算冲突。
- 证据只命中同赛事但不是同一参赛双方，不升为反证。
- 搜索页、入口页、无正文页仍不能绕过 page/slot gate。

### 我应该怎么使用

调试时重点看这些字段：

- `atomic_claims`
- `atomic_query_plan`
- `atomic_refuted_points`
- `atomic_label_pressure`
- `atomic_claim_route_debug`
- `final_result._decision_policy`

如果 `atomic_refuted_points` 有强反证，但最终标签没变，要优先检查聚合层或 review 层是否覆盖了 `atomic_core_direct_refutation`。

### 对用户意味着什么

用户会看到系统更像人工标注员：不是笼统说“这个赛事答案可疑”，而是能指出“某一行表格的具体小局分被退赛/不战而胜证据反驳”。这让 reason 更可追溯，也更接近标准答案关心的小而硬事实点。

### 对开发者意味着什么

开发者后续不应该为某个运动员或某个样本写规则，而应该继续扩展“结构形态 + 风险类型 + 槽位一致性”的转换器。例如：

- 表格行转换器继续服务其他赛事。
- `phase_boundary_time` 应做阶段词和时间边界转换。
- `exclusive_or_only_path` 应做唯一性断言和替代路径转换。

### 当前结论

这轮证明了“原子 claim -> 对照检索 -> 同槽反证账本 -> 聚合标签”的链路可以打通，而且是通过通用结构完成的，不依赖样本专名真值。

但还要注意：`afc_0004` 的输出 reason 里证据值仍然偏工程化，例如 `withdrawal_or_walkover`，下一步需要把 evidence sentence 和 evidence value 展示得更自然。

### 下一步建议

下一步优先做 `phase_boundary_time` 的同类转换器：

1. 把“第一阶段/第二阶段/开始/结束/公布”拆成阶段边界槽。
2. 区分“第二阶段开始”与“整个人口普查结束/结果公布”。
3. 只在同一主体、同一阶段、同一时间边界明确冲突时进 `atomic_refuted_points`。
4. 同时修 reason 展示，让原子反证输出原句而不是内部枚举值。
