# AFC 事实核查提交说明

本提交面向 `factcheck-20260325-v1` 任务，目标是对给定问答样本进行事实核查，并输出三分类标签：

- `0-主需存在事实错误`
- `1-次需存在事实错误`
- `2-无事实错误`

正式提交链路以 `solve.py -> output/results.json` 为准。`README.md` 只说明方案设计、运行方式和重点版本演进。

## 整体流程

当前方案不是单轮黑盒分类，而是结构化事实核查流程：

```text
读取输入(question / answer / time / history_question)
-> 大模型抽取用户需求、事实声明、检索语句与纠偏线索
-> retrieval.py 执行网页检索、页面诊断、纠偏重试与候选句收集
-> evidence.py 生成事实声明级证据摘要、支持点、反驳点、证据点候选与覆盖度
-> 大模型基于证据做事实裁决、错误严重性判断、理由草案与初步标签
-> 代码结合需求类型、证据覆盖、证据直接性和理由一致性做最终聚合
-> 写入 output/results.json
```

设计重点：

- 先判断回答实际声称了什么，再判断真假、证据覆盖和错误级别。
- 大模型负责语义理解、事实声明拆解、检索规划、纠偏判断和初步裁决。
- 代码负责检索执行、来源过滤、证据预算、断点续跑、页面效用控制和最终聚合。
- 外部检索只作为证据获取模块，不依赖模型自身联网能力。
- 正式链路只生成 `output/results.json`，调试文件、报告和本地评估不属于提交输出。

## 运行方式

默认输入为当前目录下的 `data.json`，默认输出为：

```text
output/results.json
```

运行示例：

```powershell
python solve.py --workers 4
```

如需显式指定输入输出：

```powershell
python solve.py --input data.json --output output/results.json --workers 4
```

运行控制：

- 默认并发为 `4`，属于保守并行，避免大模型接口限流或超时。
- `solve.py` 会边运行边刷新 `output/results.json`，中断后可续跑未完成样本。
- 如需强制全量重跑，可使用 `python solve.py --workers 4 --no-resume`。
- 提交版 `solve_submit.py` 从当前 `solve.py` 同步生成，并关闭磁盘缓存输出。

## 版本演进

当前版本关系：

- 旧 `v2` 对应历史单脚本实现 `solve_v1.py`，是“能跑通”的基线。
- `v3` 对应结构化 AFC 主链，重点解决“能检索、能解释、能聚合”。
- 当前 `v4` 已从证据句级与检索纠偏推进到 evidence-first 主线，重点解决“检索缺口能纠偏、证据点能成型、旧兜底要退权”。

### 2026-05：v4 第四阶段，evidence-first 主线与证据事件层

本阶段把目标从“让标签看起来对”，推进为“让最终标签尽量由真实证据链推出”。

- 将主链明确拆成 `retrieval -> page retention -> point conversion -> aggregation/calibration` 四层，先看证据在哪一层断，再决定该修检索、页面、点位还是聚合。
- 调试顺序固定为先看 `evidence_events`，再看 `point_conversion`，再看 `aggregation`；只有没有可裁决证据时，才允许兜底介入。
- 将对象绑定、页面契约、点位契约、时间范围等信息纳入 direct/refuting point 判定，减少“相关页”或“像答案的句子”冒充可裁决证据。
- 明确 evidence-first 原则：`uncertain` 不能伪装成 `refutation`，没有真正成立的反证点时，不再让旧校准层偷偷改写标签来源。
- 代表性结论：当前主要瓶颈已从“完全搜不回页面”，转向“页面回来了但对象没绑稳、句子没成点、证据还没真正接管裁决”。

### 2026-05：v4 第四阶段，对象绑定驱动纠偏与 route / numeric / date 成点收口

本阶段重点把“按缺口补救”真正接进主链，并继续收紧路线类与结构化 claim 的可裁决点口径。

- retry 从 coverage-first 推进为 `object_binding + gap_layer` 驱动，按 `search_recall`、`page_contract`、`point_grounding`、`time_scope` 等缺口选择不同 operator family，而不是泛化重试。
- route 主链补入受约束的 LLM 判点上下文，coverage 不再把对象锚点未绑定的 uncertain point 记成 direct route evidence。
- 结构化 numeric / date claim 开始优先消费满足页面契约的结构化点，并强化 `time_scope_binding`，避免拿错年份、错时点的金额或日期当成直接反证。
- point grounding 不再只看句子像不像答案，而是显式消费 `evidence_contract_status / role`、`point_contract_status` 等信息，把背景页和伪直证更早挡掉。
- 阶段结论：系统已能更稳定区分“搜到了但被错杀”“搜到了但没成点”“点相关但时点不对”，但 route 主需强反证与 structured point 直达 verdict 仍在继续收口。

### 2026-05：v4 第四阶段，旧兜底缩权与 fallback 边界重构

本阶段开始系统性收缩最终裁决层的旧语义兜底权限，让主链逐步拿回标签解释权。

- 审计 `semantic_audit`、`regression_label_calibration` 等旧接管点，区分“只告警”“可解释”“仅在无可裁决证据时兜底”三类权限边界。
- 第一批缩权先处理 `secondary_detail_direct_refutation`，让 `0004` 这类次需直接反证不再主要依赖 `semantic audit` 判对，而是尽量由聚合层自己接住。
- 固化两个原则：一是已成立的次需 direct refutation 不应再被旧校准层抹回 `2`；二是 `uncertain_points` 不能再被宽口径包装成真正的 `refuting_points`。
- 同步清点旧分支仍会抢标签、抢 reason 的位置，为后续把散落补判逻辑收成统一的新 fallback 区做准备。
- 当前结论：phase4 已经开始把部分标签来源从旧兜底链挪回 evidence-first 主线，但 fallback 仍需继续产品化和限权。

### 2026-05：v4 第四阶段，任务语义卡与 LLM 在线编排接线

本阶段把 LLM 从零散 prompt 使用，推进为可观察、可约束的上游语义编排层。

- 将 `task_semantics` 接入 `verification_plan -> source_intent -> evidence_task_card`，让语义任务卡真实参与 query plan、检索意图和对象约束，而不是只靠裸 query 猜题型。
- LLM 角色开始收口为 `claim compiler`、`gap diagnosis`、`operator selector`、`page / point contract helper`、`constrained verdict helper` 五类在线角色。
- 新链路强调“开放理解 + 有限执行”：先编译主需/次需、对象、指标、时间范围和证据形态，再驱动检索、纠偏、判点与最终裁决。
- 已观察到 `semantic_task_probe` 和任务语义卡真实进入检索与调试链路，说明这不是停留在文档层的空接线。
- 阶段结论：语义卡与在线编排已开始产生正向增益，但路线类核心题仍可能回落，且当前耗时距离正式 `100题 / 90分钟` 约束还有明显差距。

### 2026-05：v4 第三阶段，检索质量判定与纠偏闭环

本阶段把检索从“搜完再看结果”，推进为“先判断检索质量，再根据缺口选择下一步怎么补救”。

- 新增检索质量分、失败阶段、缺口标记和建议动作，把“没搜好”拆成可解释的失败画像。
- 接通“换检索源”“按页面意图重搜”“根据缺口生成目标页面描述再检索”等纠偏动作，让这些动作进入真实执行计划。
- 增加查询来源和查询目标诊断，能看出一条检索语句来自模型原始规划、页面探针，还是失败后的兜底重试。
- 参考自动事实核查和检索增强生成中的做法，把主链明确为：先判定检索质量，再归纳缺口，再选择纠偏动作。
- 已验证纠偏链路能够真实执行；尚未完全解决所有路线类样本的直接证据召回，主要瓶颈仍在页面命中和句子可裁决性。

### 2026-05：v4 第三阶段，页面探针、检索源预算与召回断点

本阶段重点处理“检索词看起来合理，但搜回来的页面类型不对，或优先检索源没有结果”的问题。

- 将路线框架检索、页面形态检索、失败后的页面意图重试统一到“按目标页面检索”的链路中，目标是召回路径说明页、分析页、带关键段落的正文页。
- 把召回失败拆成几类：检索源报错或被拦截、高优先级来源没有返回、只有低优先级兜底源有结果但又被过滤、有原始结果但全部被页面保留层挡掉。
- 检索源预算不再机械截取前几个来源，而是优先保留不同类型的来源，避免预算较小时只跑同一类网页源。
- 页面探针获得受控兜底：不打开全局无限扩散的重试，只在目标页面明确、价值较高的查询上补跑。
- 代表性结论：部分问题已从“完全搜不回来”推进到“页面能回来但不够可裁决”，说明召回层阻塞被拆开了一部分。

### 2026-05：v4 第三阶段，路线类探针收口与通用化
 
路线类事实只作为高敏感探针使用，不再发展成一套厚重的专项规则。

- 路线检索先抽取“主体是谁、要查什么区域或对象、需要什么路线关系、时间窗口是什么、需要怎样的证据句”，再生成检索语句。
- 页面保留逻辑从长串条件判断收成“页面能力画像”，以后其他事实类型也可以复用同样的页面判断框架。
- 句子最低可用性判断开始消费已有诊断信号，降低事件背景句、泛泛导弹背景句被误判成直接证据的风险。
- 来源过滤增加窄口径误杀修正，只救“页型接近、保留分不低、已有强候选句”的页面，不放宽整类背景页。
- 当前结论：路线类主要失败不再是“路线关系词不够”，而是页面保留、正文抽取和可裁决路线句不稳定。

### 2026-05：v4 第三阶段，代码审计与命名收口

本阶段集中清理会影响后续审计判断的历史残留。

- 删除或断开旧的路线类回退链路，只保留新的主线页面探针，避免多套旧逻辑同时竞争。
- 将“背景页、汇总页、入口页”这类页面形态信号改成通用命名，不再挂在路线类专项名下。
- 将“北部、南部、东部、西部”等方向修饰处理收成通用的地理锚点归一化能力。
- 将“报道、报告”等检索壳词收成通用查询噪声词，减少检索语句被无意义词污染。
- 清理 `evidence.py` 中重复定义的路线类旧实现，避免同名函数覆盖导致“看起来有很多逻辑，实际只有最后一版生效”的审计误差。

### 2026-04：v4 第一阶段，证据句统一输出

本阶段把证据粒度从网页级摘要推进到句子级候选可观察。

- 新增统一的证据句收集入口，为每条事实声明输出候选证据句。
- 路线、数值、日期、实体、事件结果等事实类型都开始挂出候选证据句，避免只有少数类型具备句级入口。
- 本地平台增加候选证据句统计和展示，可以直接看到每个事实声明有哪些候选句。
- 这一阶段不改最终验证和标签聚合，目标是先把“每个声明当前到底有哪些候选句”稳定暴露出来。
- 验证结论：样本调试文件中已出现统一的候选证据句字段，说明句级候选输出层成立。

### 2026-04：v4 第二阶段，句级评分与证据点转换诊断

本阶段解决“有候选句，不等于能形成证据点”的中间断点。

- 在候选句上显式区分“直接回答、部分相关、只是相关但不能裁决”，并记录句级评分。
- 新增候选句到证据点的转换诊断，统计候选句数量、直接句数量、部分相关句数量、支持点、反驳点和不确定点。
- 平台可以区分“没有候选句”“只有相关句”“没有直接句”“缺少路线关系句”等失败状态。
- 路线类进一步拆出“缺少路线关系句”，避免把“没有路线关系句”误看成普通相关不足。
- 阶段收益是诊断能力提升，不是直接提分；它让下一步能判断该改检索、句子可用性，还是证据点选择规则。

### 2026-04：v3.54-v3.58 最终理由收口

本阶段处理最终理由与标签、证据链之间的冲突。

- 增加最终理由冲突检测，识别“标签为 0/1 但理由说只能判 2”等自相矛盾输出。
- 试验并回收过强模板，逐步让模板退出正常输出路径，把理由主导权还给证据链和模型精修。
- 平台增加最终理由一致性诊断，用于区分标签正确、理由错位、证据未绑定等情况。
- 稳定结论：理由不能写成“代码聚合校准为某标签”，而应引用决定标签的事实声明和证据点。

### 2026-05：v4 phase4 证据可比性、support 收紧与 news/official 并行

这一轮不再继续靠“相关页面 + 语感风险”硬推标签，而是把几条关键边界正式写进代码合同。

- 给 numeric/date/result 类证据补了 comparability contract，只允许在同一事实位点上做 direct support / direct refute。
- `refute` 可以 early exit，但 `support` 不再 early exit；核心支持后仍需继续检查高风险 supporting/peripheral detail。
- `supporting/peripheral` 的结构化细节默认优先留在 `2`，只有直接反证或可稳定逻辑反推时才升到 `1`。
- news 链路重新恢复为 event/date/current-status 类题目的正式证据通道；官方页仍继续增强，但不再压掉新闻召回。
- claim 抽取补了排他性 premise 覆盖，例如 `唯一 / 只能 / 必经 / 完全绕开`，避免这类 gold 对应错误点只留在解释层。
- submit 版同步了这轮已经相对稳定的行为：排他性 premise claim 增强、相关 supporting claim 保留、以及 `census_phase/current_status` 这类核心日期题的 query budget 放宽。

### 2026-04：v3.43-v3.49 候选句、证据重排与理由来源链

本阶段把正文候选句和最终理由绑定接到主流程。

- 从标题、摘要、详情页正文中抽取更像可裁决证据的句子。
- 候选句进入证据重排，优先选择直接回答事实声明的句子，而不是整页相关材料。
- 最佳候选句进入证据摘要主链，并作为最终理由的优先材料。
- 平台展示理由来源链，开始能追踪最终理由来自证据句、提示性理由，还是兜底生成。
- 这阶段为 v4 的句级证据链奠定了过渡层。

### 2026-04：v3.27-v3.42 核查问答链与检索策略评估

本阶段把事实声明核查拆成“核查问题 -> 证据答案 -> 支持/反驳/未知”的中间结构，并建立检索策略评估工具。

- 新增核查问题和问答证据链，把每条事实声明转成可回答的核查问题。
- 验证输入开始包含压缩后的问答证据，并明确“未知”或“没有证据”不能包装成事实错误。
- 新增检索策略对比评估脚本，统一比较基线方案、来源健康度预检、首条结果预检、自适应兜底等策略。
- 策略推荐采用保守口径：新策略只有在理由质量不退、耗时不过高、坏结果比例不变差时才建议启用。
- 这一阶段建立了“策略是否有效要看理由、证据链、耗时和污染率”的评估习惯。

### 2026-04：v3.16-v3.26 数值对齐、裁决依据与理由精修

本阶段聚焦数值、日期和最终裁决依据的可解释性。

- 增强数值对齐，减少数值、单位、日期窗口不一致导致的误判。
- 裁决依据与理由忠实约束进入主链，最终标签需要能回指到具体事实声明与证据。
- 平台补充分项评分体系，开始从标签、理由、证据覆盖、同因程度等维度联合评估。
- 模型理由精修与代码兜底并行存在，但逐步收紧为“证据链优先、模板兜底只处理异常”。

### 2026-04：v3.9-v3.15 检索源规划与性能优化

本阶段从“搜什么”扩展到“去哪类来源查”，同时控制正式运行耗时。

- 让模型输出检索来源类型、检索渠道、语言偏好、必须命中的证据要素和应避免的弱来源。
- 代码负责把检索意图映射成实际来源计划、约束可信域名、评分并回退低质量来源规划，避免模型直接编造域名或滥用站内搜索。
- 官方来源发现、结构化噪声惩罚、检索源规划净化逐步接入。
- 抽取快速模式、低价值改写收紧、首轮检索预算控制等优化用于稳定正式运行时间。
- 这阶段形成“模型负责规划，代码负责执行、过滤、预算和回退”的边界。

### 2026-03：v3.1-v3.8 证据优先与风险校准

本阶段从 v2 的可运行系统过渡到 v3 的原因链系统。

- 明确“证据不足不等于事实错误”，没有直接支持或反驳时一般不能把低覆盖直接判为 0/1。
- 恢复语义边界审计，但要求它与证据覆盖、事实声明重要性共同聚合，不能单独强推标签。
- 引入证据目标、证据缺口、风险字段与聚合护栏，减少靠风险词或表达风格误判。
- 最终理由开始绑定决定性事实声明：判 0 写主需反证，判 1 写次要事实反证，判 2 写关键事实未被直接反驳。

### 2026-03：v2.27-v2.43 提交候选、Playwright 兜底与主脚本收口

本阶段把开发调试版本推进为可提交、可控时、可续跑的候选版本。

- Playwright 作为条件触发兜底，而不是默认替代所有检索。
- 开发版保留调试、耗时统计、报告和本地评估；提交版只保留读取输入、执行主链、写出 `output/results.json`。
- 主脚本强化断点续跑、并发控制、短超时、有限重试和输出清理。
- 用户需求类型、证据模式、风险类型等抽象字段接入主流程，为后续去题面化和风险聚合提供结构。
- 稳定结论：提交路径必须最小化，诊断能力留在开发平台中。

### 2026-03：v2.1-v2.14b 检索诊断、证据覆盖与去题面化

本阶段完成“事实声明拆解 + 外部证据检索 + 证据裁决”主骨架的早期成型。

- 从早期单脚本判断演进为“用户需求 -> 事实声明 -> 检索 -> 证据 -> 裁决 -> 严重性 -> 最终标签”。
- 引入检索失败诊断，区分无结果、弱来源、时间窗口错配、详情页读取失败、缺少直接证据等情况。
- 首轮证据不足时由模型根据失败原因改写检索语句，而不是在代码里堆样本关键词。
- 证据覆盖开始判断实体、时间、直接回答程度和证据强度，减少相关但不直接的网页进入裁决。
- 这一阶段确立了项目原则：不追求“猜对标签”，而追求“证据链能解释为什么对或错”。

## 总结

旧 `v2` 解决“能跑”，`v3` 解决“能检索、能解释”，当前 `v4` 解决“能诊断、能纠偏、能把证据落到句子”。

核心改进不是堆关键词，而是把 AFC 拆成可诊断、可复核、可控制预算的事实核查流程。
